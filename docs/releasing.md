# Releasing & versioning llamawizard

A self-contained, no-AI-needed guide to bumping the version and cutting a release.
Read this top-to-bottom once; after that you only need the **Quick reference** at the
bottom.

---

## The one idea to internalize

**The version is the git tag. Nothing else.**

There is no version number written anywhere in the source code that you edit by hand.
`cmd/llamawizard/main.go` has `var version = ""` and fills it at build time:

- **Release builds** — GoReleaser stamps it from the tag via
  `-X main.version={{.Version}}`. Tag `v0.1.5` → binary reports `0.1.5`.
- **Local dev builds** (`go build` / `go install`) — it falls back to Go build info,
  which gives you a `git describe` string like
  `v0.1.5-0.20260819142820-030bac6f1f73`. That long suffix is normal locally; it just
  means "tag + how many commits after + which commit." It is **not** a mistake.

So: **releasing = creating a tag and pushing it.** Everything after that is automatic.

```
you push tag v0.1.5
        │
        ▼
.github/workflows/release.yml  (triggered by: on: push: tags: "v*")
        │
        ├── CI (tests must pass)
        ▼
GoReleaser  →  builds darwin amd64 + arm64
             →  uploads tar.gz + checksums.txt
             →  creates the GitHub Release "v0.1.5"
             →  auto-writes the release notes from your conventional commits
```

You never run GoReleaser yourself. You never edit a version string.

## Semver — which bump do I pick?

Follows [Semantic Versioning](https://semver.org). The three `task` commands:

| Command | Bumps | Use when |
|---|---|---|
| `task release:patch` | `0.1.4 → 0.1.5` | Bug fixes, small features. **This is your default.** |
| `task release:minor` | `0.1.5 → 0.2.0` | A new user-facing feature / new command, backward compatible. |
| `task release:major` | `0.2.0 → 1.0.0` | Breaking change (CLI flags removed, config format changes, etc.). |

When in doubt between patch and minor: if a user upgrading won't have to change anything, it's a **patch**.

> Pre-1.0 note: this project is `0.x`, where "minor" bumps are also used liberally for
> features. That's fine and conventional for pre-1.0 software.

## The normal flow (feature → release)

This is the full happy path. You've already done most of it with the planner/runner.

### 1. Build the feature on a branch

```bash
git checkout main && git pull
git checkout -b feat/my-feature
# ... work, commit, test ...
git push -u origin feat/my-feature
```

### 2. Open a PR and merge it

Open the PR on GitHub. CI runs automatically (`.github/workflows/ci.yml` on
`pull_request`). Once green, **merge it into `main`**.

> Merge style doesn't matter for versioning — the tag is what counts, not the commit.

### 3. Cut the release (one command)

```bash
git checkout main && git pull     # make sure main has the merged work
task release:patch                # or :minor / :major
```

That single command does all of this (see `Taskfile.yml` → `_bump`):

```bash
latest=$(git describe --tags --abbrev=0)     # finds v0.1.4
# ... computes next = v0.1.5 ...
git tag -a "v0.1.5" -m "v0.1.5"              # annotated tag
git push origin "v0.1.5"                     # pushes the tag
```

You'll see: `Tag v0.1.5 pushed — GoReleaser will now publish the release.`

### 4. Watch it go out

- Actions: https://github.com/eduard-lt/llamawizard/actions — the **Release** workflow
  runs CI then GoReleaser. ~1–3 minutes.
- Result: https://github.com/eduard-lt/llamawizard/releases — a new `v0.1.5` with the
  two `.tar.gz` archives, `checksums.txt`, and auto-generated notes.

That's the whole release.

## Verifying a release (2 minutes, worth doing once per release)

Download the release artifact for your arch and run it:

```bash
# from the release page, grab llamawizard_0.1.5_darwin_arm64.tar.gz
tar xzf llamawizard_0.1.5_darwin_arm64.tar.gz
./llamawizard version
```

Expected — note the **clean** version (no date/commit suffix), proving it was stamped
from the tag:

```
llamawizard: 0.1.5
llama.cpp:   10360 (48d22e295)
llama-swap:  v245 (30470a4)
```

(If you see `v0.1.5-0.2026...-<hash>`, you're running a local/dev build, not the
release artifact.)

## The in-repo CHANGELOG.md (optional, separate from the release notes)

The **GitHub release notes** are auto-generated by GoReleaser — nothing to do.

The `CHANGELOG.md` file that lives in the repo is a *separate* artifact generated by
[git-cliff](https://gitcliff.org) from your conventional commits:

```bash
task changelog          # rewrites CHANGELOG.md (needs git-cliff: brew install git-cliff)
git commit -am "chore: update changelog for v0.1.5"
git push
```

Do this after the tag if you want the in-repo file to stay current. It's optional —
the release page is the source of truth for what shipped.

## Things you do NOT do (the "not fully depend on AI" part)

- ❌ Do **not** hand-edit any version number in Go code. There is none to edit.
- ❌ Do **not** run `goreleaser` locally. The workflow does it with the right
  permissions and Go toolchain.
- ❌ Do **not** edit `Formula/llamawizard.rb` to bump a version — it's a **head**
  formula that always builds from `main`, so there's no pinned version to update.
- ❌ Do **not** push a tag like `0.1.5` (no `v`) or `v0.1.5-rc1` casually — the release
  workflow matches `tags: "v*"`, and the bump tasks expect a clean `vX.Y.Z`.
- ✅ Conventional commit messages (`feat:`, `fix:`, `chore:`, `docs:`…) are what make
  the auto release notes readable. Keep writing them that way.

## If something goes wrong

| Situation | Fix |
|---|---|
| Tagged the wrong version by mistake | Delete the tag locally and remotely, re-run the bump: `git tag -d v0.1.5 && git push origin :refs/tags/v0.1.5` then `task release:patch` again. |
| Release workflow failed | Open the Actions run, read the log. Usually a test failure — fix, push to `main`, delete the bad tag, re-tag. |
| Tag pushed but you want to re-do notes | Edit the release notes directly on the GitHub release page (doesn't affect binaries). |
| Accidentally released from a dirty/wrong branch | Same as "wrong version": delete tag, get back to clean `main`, re-run. |
| Want to yank a release | GitHub → Releases → Edit → uncheck "This is a pre-release" / or Delete release. The tag stays; just remove the published assets if needed. |

> Deleting a tag is always safe to *try* — nothing downstream breaks until you push the
> corrected tag. The only real constraint: don't reuse a version number for different
> content.

## Quick reference

```bash
# --- everyday ---
git checkout main && git pull
task release:patch          # 95% of releases
task release:minor          # new feature, backward compatible
task release:major          # breaking change

# --- check where you are ---
git tag --list 'v*' --sort=-v:refname | head   # list versions, newest first
git describe --tags                            # latest tag + distance from HEAD
llamawizard version                            # what the current binary reports

# --- optional in-repo changelog ---
task changelog && git commit -am "chore: update changelog" && git push
```

**Mental model:** write the feature → merge to `main` → `task release:patch` → watch
Actions → done. The tag *is* the version.
